# 템플릿 — DEV-65 테스트명세서 (v2.1)

> **v1 기준본 양식.** 고칠 때는 이 파일과 헌법 §0을 함께 본다.
> **용도:** 헌법 §5의 「테스트 범위·기준」. 제품당 파일 하나.
> **경로:** `{docs_root}/DEV-65-테스트명세서.md`
> **가독성:** 표 우선. 산문은 이 양식의 규칙만.

이 유형은 `_tools/docs_draft_cli.py`의 생성 대상이 아니다. 초안은 아래 펜스를 복사한 뒤 칸을 바꾼다.

## 표기

| 기호 | 의미 |
|---|---|
| ＊ | 필수. 스키마 `required` |
| ○ | 권장. 스키마 `optional` |
| □ | 선택 표기. 이 유형 스키마에는 □ 절이 없다 |

## 이 문서와 이웃

| 질문 | 적는 곳 | 적지 않는 곳 |
|---|---|---|
| 무엇을 시험하고 무엇을 시험하지 않나 | ＊ 범위 | 기능의 통과 조건 본문은 DEV-22. 케이스 칸에 그 조건의 ID를 적을 수 있다 |
| 어떤 사전·절차·기대를 보나 | ＊ 필수 시나리오 | 한 구현 작업의 검증 명령은 DEV-70. 여기에는 그 명령이 이 스위트의 어디인지 위치를 적는다 |
| 스위트가 끝났다고 볼 조건 | ＊ 완료 조건 | 성능 숫자와 재현 절차는 DEV-68 |
| 재현을 깨는 시험 방식 | ＊ 금지·픽스처 주의 | 제품이 하지 않는 일은 DEV-20의 비범위 |
| 시험이 어디에 닿나 | ○ 테스트 크기 | 스위트 비율은 적지 않는다. 통과 조건 본문은 DEV-22 |

필수 프로필에 이 코드는 없다.

## 문서 성숙도

| 상태 | 이 유형에서 |
|---|---|
| draft | 필수 네 절이 lint를 통과. ＊ 범위는 1행이면 기계는 통과한다 |
| 리뷰 | active 전에 범위에 '시험하는 것'과 '시험하지 않는 것'이 둘 다 있게 보강 요청을 남긴다 |
| active | 시나리오의 기대가 DEV-22가 있으면 그 조건과 같고, 없으면 기대 칸에 그 조건 문서가 아직 없다고 적는다 |
| deprecated | 시나리오를 빼면 행을 지우기보다 기대 칸에 폐기와 대체 케이스 ID를 적는다 |

이 저장소에는 유형별 이상형 체크리스트 파일이 없다. `_tools/ideal_check_min.py`는 DEV-10·DEV-30만 본다. 사람 검토를 못 채운 것은 헌법 §1.5.5대로 draft 실패가 아니다.

## 사람 검토

스키마 label은 복사용 H2로 한 번만 있다.

| 항목 | 칸에 쓸 내용 |
|---|---|
| ＊ 범위 | 시험하는 것을 적는다. 열 `구분`·`내용`, 최소 1행. 구분은 자유 글이다 |
| ＊ 범위 | 시험하지 않는 것을 다른 행에 둔다. 시험하지 않는 이유에 '범위 밖'만 반복하지 않는다 |
| ＊ 필수 시나리오 | 절차는 재현 순서만 적는다. 열 `케이스`·`사전`·`절차`·`기대`, 최소 1행. 네 칸은 서로 다른 사실이다 |
| ＊ 필수 시나리오 | 기대는 관측할 결과만 적는다. Gerard Meszaros의 Four-Phase Test(xUnitPatterns.com, 책 358쪽)는 사전을 실행 전 그림만, 기대를 그 결과만 적으라고 한다. 다른 케이스의 사후 상태와 아직 정하지 않은 질문은 그 칸에 두지 않는다 |
| ＊ 완료 조건 | 조건은 스위트를 끝으로 볼 관측이다. 열 `#`·`조건`, 최소 1행 |
| ＊ 완료 조건 | 실행 파일의 유무는 그 칸에 두지 않는다 |
| ＊ 완료 조건 | Cucumber Gherkin의 Then은 기대 결과이고, 그 결과를 돌릴 도구는 아니다 |
| ＊ 금지·픽스처 주의 | 열 `금지`·`이유`, 최소 1행. 금지는 재현을 깨는 방식, 이유는 그때 깨지는 결과다. 금지가 없으면 금지 칸에 그 사실을 적는다. |
| ○ 테스트 크기 | 크기는 네트워크·데이터베이스·파일·외부 시스템에 닿는지로 나눈다. 열 `크기`·`닿는 곳`·`위치`. Google 테스트 블로그의 Test Sizes(2010-12-13, Simon Stewart)는 단위·통합·E2E라는 이름 대신 그렇게 나눈다. 비율과 닿는 곳을 한 칸에 두지 않는다. 크기를 정하지 않았으면 크기 칸에 그 사실을 적고 작음·중간·큼을 짓지 않는다. 그 글의 초 제한은 여기로 옮기지 않는다 |
| ○ 테스트 크기 | 위치는 있는 경로이거나, 파일이 없으면 아직 없다는 문장이고 미결에 만들 위치를 적는다 |
| ○ 관련 문서 | 열 `코드`·`경로`. 있는 파일만. |

헌법 §1 원칙 2대로 같은 사실을 복붙하지 않는다. 반복되는 사실은 `_schemas/fact-owners.json`의 id를 쓴다. 주인 문서가 그 사실을 한 번 적고, 다른 문서는 id와 경로만 인용한다. 값이 없는 id `HC-REPO`, `HC-DRIFT-VER`, `HC-HASH`, `HC-PKG`, `HC-LEGAL`, `HC-CHANNEL`은 비워 둔다. `HC-STREAK`의 주인은 DEV-30, `HC-DRIFT-STATE`의 주인은 DEV-50, `HC-FLAG`의 주인은 DEV-52, `HC-MIDNIGHT`의 주인은 DEV-70, `HC-PLATFORM`의 주인은 DEV-10, `TOOL-PY`의 주인은 `README`, `TOOL-EXIT`의 주인은 `_tools/README.md`이다.

## 기계 검사

기준 파일은 `_schemas/DEV-65.schema.json`과 `_tools/docs_lint.py`다.

| 항목 | 기준 |
|---|---|
| 경로 | `{docs_root}/DEV-65-테스트명세서.md` |
| 위치 | 단건. 폴더 안 파일은 `DOC_PATH` |
| 헤더 | `상태`·`코드`·`마지막 갱신`·`범위`·`비범위`. 코드는 `DEV-65`. 날짜는 달력의 `YYYY-MM-DD` |
| 제목 | `^#` 줄에 `DEV-65`가 단어로 있다 |

| 필수 제목 | 열 순서 | 최소 행 |
|---|---|---|
| ＊ 범위 | 구분, 내용 | 1 |
| ＊ 필수 시나리오 | 케이스, 사전, 절차, 기대 | 1 |
| ＊ 완료 조건 | #, 조건 | 1 |
| ＊ 금지·픽스처 주의 | 금지, 이유 | 1 |

선택 절의 열 이름은 `check_file`이 필수 절에만 맞춘다. 복사용 본문은 스키마 columns를 쓴다. 필수 칸의 `…`, `TBD`, `TODO`, `-`, `—`, `YYYY-MM-DD`는 `FAKEFILL`이다. 판정은 `_tools/docs_common.py`의 `placeholder`다. 선택 표의 `…`는 `FAKEFILL`이 아니고 빈 칸은 `EMPTY_CELL`이다. 미결 열은 `ID`·`미결`·`다음에 할 일`이다. 스키마 `rules`는 실행되지 않는다.

## 작성 규칙

- 헤더 범위는 이 스위트, 헤더 비범위는 성능 목표(DEV-68)와 인수 조건의 전문(DEV-22)이다. 본문 ＊ 범위 표와 헤더 범위는 같은 경계를 다른 길이로 적는다. 두 곳이 서로 다른 경계이면 사람 검토에서 맞춘다.
- 크기 행은 시험이 닿는 곳만 적는다. 스위트에서 차지하는 비율을 적지 않는다. 크기를 정하지 않았으면 이름을 짓지 않는다.
- 실사용자 데이터와 비밀을 픽스처 예로 적지 않는다.
