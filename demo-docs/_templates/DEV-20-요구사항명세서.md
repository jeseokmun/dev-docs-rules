# 템플릿 — DEV-20 요구사항명세서 (v2.1)

> **v1 기준본 양식.** 개정할 때는 이 템플릿과 헌법 §0을 함께 고친다.
> **경로:** `{docs_root}/DEV-20-요구사항명세서.md` (단건, 문서 루트)
> **용도:** 헌법 §5. 무엇을 만드는지와 비범위.
> **가독성:** 표 우선. 산문은 요약 1–3문장 (헌법 §1.11).

## 표기

| 기호 | 의미 |
|---|---|
| ＊ | 필수. 헌법 §1.9 |
| ○ | 권장 절. 제품 문서에서 빼도 필수 검사에는 없다 |
| □ | 헤더에 있으면 그 칸은 빈 값·자리표시의 lint 예외 |

## 문서 성숙도

| 단계 | 이 유형에서 |
|---|---|
| draft | ＊ 다섯 절이 lint를 통과하면 된다 |
| 모르는 값 | 요구를 지어 넣지 않는다. 칸은 `미결`, 미결 표에는 다음에 확인할 일 |
| 리뷰 | 보강 요청은 채울 요구의 목록이다 |
| active | 핵심 미결이 닫히고, 완료의 정의로 끝났는지 다시 볼 수 있을 때 |
| 어긋남 | 구현이 요구와 다르면 요구를 고친다 |
| 어긋남 | 고치지 못하면 상태를 deprecated로 둔다 |

## 사람 검토

항목 이름은 복사용 본문의 제목과 같다.

| 항목 | 사람이 볼 것 |
|---|---|
| ＊ 목표 | 이번 범위에서 만들 결과가 요약 1–3문장이다 |
| ＊ 비범위 | 만들지 않을 항목과 이유가 한 행이다. 최소 2행. 이유만 `미결`이면 lint는 통과하고, 사람 검토는 이유를 요구한다 |
| ＊ 사용자·장면 | 누가 쓰는지. 행 키는 사용자·장면만 허용된다. min_rows가 1이라 확인된 키만 있어도 된다. 모르는 키는 행 없이 미결에 둔다 |
| ＊ 사용자·장면 | 어느 장면에서 쓰는지. Jakob Nielsen의 Usability 101(2012-01-03)은 필요한 기능과, 그 일을 얼마나 빨리 하는지를 나눈다. 장면 칸은 하는 일만 적고, 걸리는 시간은 ○ 비기능에 둔다 |
| ＊ 기능 요구 | 요구 칸은 만들 일만 적는다. 최소 3행. 측정하지 않은 숫자는 ○ 비기능의 `추측:` 규칙을 따른다 |
| ＊ 기능 요구 | 검증 힌트는 그 요구를 확인할 절차의 이름이다. Bill Wake의 INVEST(2003-08-17, Testable)는 확인을 이야기 카드의 세부 문장으로 두지 않는다. 검증 힌트는 인수 조건을 가리키고, 그 조건의 문장을 다시 적지 않는다 |
| ＊ 완료의 정의 | 무엇을 보면 이 명세의 범위가 끝났는지. 최소 2행. 완료 행은 요구 번호와 확인만 적는다. 한 행은 요구 하나의 확인만 적는다. Google의 Small CLs는 변경 하나가 한 가지만 다루라고 한다 |
| ＊ 완료의 정의 | 그 순위 단어를 완료 행에 다시 쓰지 않는다. Must·Should·Could는 ○ 우선순위에만 둔다. RFC 2119(S. Bradner, 1997) 6절은 강제 단어를 요구 수준을 정하는 자리에만 쓰라고 한다 |
| ○ 비기능 | 항목만 적는다. 항목, 목표, 측정 |
| ○ 비기능 | 목표만 적는다 |
| ○ 비기능 | 측정만 적는다. 측정하지 않은 숫자에는 헌법 §1.4의 `추측:`을 붙이거나, 숫자를 쓰지 않고 미결에 둔다 |
| ○ 우선순위 | 요구 번호와 맞춘다. 합의 전이면 그 절의 자리표시 행은 두지 않는다. 미결 내용에 `없는 사실:`과 `다음 행동:`을 적는다 |
| ○ 우선순위 | 칸의 값은 열 이름이 보여주는 Must, Should, Could 중 합의된 하나이다 |
| ○ 관련 문서 | 코드와 실제 경로. 개요는 DEV-10, 인수 조건은 DEV-22일 수 있다. 없는 파일은 적지 않는다 |

사실, 결정, 추측, 미결을 한 칸에 섞지 않는다 (헌법 §1.4). 별도 H2 `사실 / 추측`은 스키마에 없다. 추측은 해당 칸의 `추측:` 접두사로 두고, 아직 모를 일은 미결 표로 보낸다. 요구 칸에 호출 방향을 적지 않는다. SEBoK의 System Requirements는 요구가 무엇을 하는지를 말하고, 구현의 어떻게는 적지 말라고 한다. 같은 결정을 다른 말로 다시 쓰지 않는다. Martin Fowler의 Ubiquitous Language(2006-10-31)는 한 개념에 한 말을 쓰라고 한다.

헌법 §1 원칙 2대로 같은 사실을 복붙하지 않는다. 반복되는 사실은 `_schemas/fact-owners.json`의 id를 쓴다. 주인 문서가 그 사실을 한 번 적고, 다른 문서는 id와 경로만 인용한다. 값이 없는 id `HC-REPO`, `HC-DRIFT-VER`, `HC-HASH`, `HC-PKG`, `HC-LEGAL`, `HC-CHANNEL`은 비워 둔다. `HC-STREAK`의 주인은 DEV-30, `HC-DRIFT-STATE`의 주인은 DEV-50, `HC-FLAG`의 주인은 DEV-52, `HC-MIDNIGHT`의 주인은 DEV-70, `HC-PLATFORM`의 주인은 DEV-10, `TOOL-PY`의 주인은 `README`, `TOOL-EXIT`의 주인은 `_tools/README.md`이다.

## 기계 검사

기준은 `_schemas/DEV-20.schema.json`, `_tools/docs_lint.py`, `_schemas/README.md`이다.

| 항목 | 기준 |
|---|---|
| 역할 | full의 추가 필수. full에서 파일이 없으면 MISSING. light에서 없어도 프로필 검사는 통과한다. 파일이 있으면 프로필과 관계없이 본문을 검사한다 |
| 경로 | `{docs_root}/DEV-20-요구사항명세서.md` |
| 위치 | 단건. 다른 경로면 DOC_PATH |
| 제목 | `#` 줄에 `DEV-20`이 단어로 있다 |
| 헤더 | 상태·코드·마지막 갱신·범위·비범위. 코드는 DEV-20. 날짜는 달력의 YYYY-MM-DD |
| 상태 | 기본 draft, active, deprecated. DOC-CONFIG `statuses`가 있으면 그 목록 |
| 자리표시 | 필수 절과 헤더에서 `…`, `YYYY-MM-DD`, `{한 조각}`, `TBD`, `TODO`, `—`, `–`, `-`, `...`, `lorem ipsum`, 빈 문자열은 실패한다. `없음`과 `미결`은 통과하는 글자이다 |
| 빈 칸 | `비고`가 아니고 `□`가 없는 헤더의 빈 칸은 문서 전체에서 EMPTY_CELL |
| 선택 절 | 열 이름을 검사하지 않는다. 복사용 열은 스키마 columns와 같다 |
| 미결 | 스키마 열은 ID·내용. 열 이름은 검사하지 않는다. 내용 칸은 `없는 사실:` 문장과 `다음 행동:` 문장이다. 빈칸은 EMPTY_CELL이다 |

| 필수 제목 | 스키마 | lint |
|---|---|---|
| ＊ 목표 | string, min 1 | 자리표시가 아닌 1자 이상 |
| ＊ 비범위 | table. 항목, 이유. min_rows 2 | 열 순서, 2행 이상, 빈 칸, 자리표시 |
| ＊ 사용자·장면 | kv_rows. 열은 구분·내용. 키는 사용자·장면. min_rows 1 | 허용 키만. 두 키가 모두 없어도 된다 |
| ＊ 기능 요구 | table. 열 순서는 #, 요구, 검증 힌트. min_rows 3 | 열 순서, 3행 이상, 빈 칸, 자리표시 |
| ＊ 완료의 정의 | table. #, 조건. min_rows 2 | 열 순서, 2행 이상, 빈 칸, 자리표시 |

한 파일만 볼 때: `python _tools/docs_lint.py {docs_root} --only DEV-20 --skip-schema-sync --summary-only`

## 복사한 뒤

비범위 2행, 기능 요구 3행, 완료의 정의 2행은 스키마 최소 행 수이다. `…`가 남아 있으면 그 필수 표는 실패한다. 사용자·장면에서 모르는 키의 행은 두지 않는다. 비기능·우선순위를 정하기 전이면 그 절의 자리표시 행은 두지 않는다. 미결 내용에 `없는 사실:`과 `다음 행동:`을 적는다. 관련 문서의 파일이 없으면 그 행을 만들지 않는다. 우선순위를 남길 때는 `요구 #`가 ＊ 기능 요구의 `#`과 같은 번호인지 사람이 맞춘다. lint는 그 번호의 존재를 보지 않는다.
